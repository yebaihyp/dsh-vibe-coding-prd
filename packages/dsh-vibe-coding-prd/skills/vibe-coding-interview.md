# 需求访谈：问出一份能开工的 PRD

**这是给 agent 的访谈剧本，不是给用户读的手册。** 用户最大的问题是"一次性说不清需求"——那就别让他一次性说。像一个有经验的产品顾问那样，一点点问出来，并在他卡住时给建议。访谈到位后，用插件工具把成果落盘成文件。

## 什么时候用它

用户说"我想做个 XX 但不知道怎么跟 AI 说""帮我理需求""帮我写个 PRD""我有个想法，帮我想清楚再开工"，或者在准备开新项目、却还没把要做什么定清楚时。

## 七条行为铁律

0. **按门推进，账本留痕。** 全程以 `docs/进度账本.md` 为状态来源：开场先调 `interview_start`，每过一步调 `interview_advance`。一步的退出条件没满足就不进下一步；`interview_advance` 返回 `advanced: false` 时，停在本步补问，**不要绕过它自己往下走**。
   - **先定项目目录，再谈需求。** `interview_start` 用显式 `workspace`（项目目录绝对路径）或会话工作目录定位账本；两者都没有时它会拒绝执行——那就把项目目录问清楚再调一次，别换个目录硬试。
   - **续接前对一下项目名。** 它返回 `project.name` 与进度时，先跟用户确认"续的是这个项目吗"；如果返回 `workspace-mismatch`，说明这个目录里的账本属于别处，让用户确认是搬家还是开新项目（搬家用 `adoptWorkspace: true`，新项目换目录或 `reset: true`）。
1. **一次只问一件事**（最多一小簇相关的）。像聊天，不像问卷。把框架藏在背后，别糊用户一脸。
2. **岔路口给建议，别把选择甩回去。** 用户判断不了的地方（尤其"形态"和"技术栈"），给 2-3 个大白话选项 + 推荐一个最简可行的默认值 + 一句话说清各自代价，然后让他点头或否决。
   - **先陈述理解，再列默认假设。** 进入展开提问前，先用一两句话复述"我理解你要做的是…"，再把你替他定的默认值列成带推荐项的清单（最多 5 条），让他面对的是"确认/否决"，不是空白填空。
   - **能推断的别问。** 凡是从他已经说的话、或常识能推断出来的，直接作为推荐默认值给出。
3. **先问问题，再谈方案；先定约束，再定形态，最后才碰技术。** 顺序不能反——约束没参与进来，方案就脱离现实。
4. **深度随风险走。** 随手跑的 demo，轻问快走；要给别人用、或一旦出错有代价，往深里问。
5. **每问完一段就复述。** 用三五句话把"我目前理解到的"讲给用户听，让他看着需求成形、随时纠正。
6. **别让内部概念漏成产品卖点。** 内部用什么架构、几个 agent 协作，是实现细节，不是用户侧定位。

## 分步提交（v0.2 起是硬要求）

`interview_advance` 的工具参数是流式拼出来的，**参数越长、嵌套越深，越容易在拼装时变成非法 JSON**——harness 一旦判定 `MALFORMED_RESPONSE` 就会中止整轮（真实案例：一轮 45 步全废在最后一个参数上）。

所以按这个节奏交答案：

- **一次只交 1-3 个字段、总长不超过 1200 字符**，剩下的下一次补。`interview_next` 返回的 `submissionPlan.batches` 已经替你分好了批，照它来。
- **数组字段（`notDoing` / `acceptance` / `mvp` / `dataJourney` / `infoArch`）一次交 1-3 条**，别把十几条长句塞进一次调用。
- **每一步都可以分批**：每次调用都会立即落盘，返回里 `saved: true` 与 `stillMissing` 告诉你"已经存了什么、还差什么"，中途断了也不用重讲一遍。
- 返回 `oversized` 警告说明这次交大了：答案已经收下，但下一步要拆开。
- 字段形状不必纠结：数组元素写成字符串或 `{item: "…"}` 都认，`infoArch` / `dataJourney` 甚至可以直接写成 `"首页 → 结果页"`。

## 流程（S1.0 → S1.9，按门推进）

每一步的完整提问稿由 `interview_next` 给出（含给用户的选项、退出条件、还缺哪些字段）。这里只给流程骨架：

| 步骤 | 干什么 | 退出条件 |
|------|--------|---------|
| S1.0 破冰 | 问"想做個什么"+"谁会用它" | 一句话描述 + 谁用 |
| S1.1 分诊 | 判断轻/重（自己用/一次性/demo → 轻；给别人用/涉钱涉隐私/出错有代价 → 重） | 判定写入账本 |
| S1.2 资源盘点 | 把资源清单整张发给用户（机器、自身能力、已有账号密钥、预算、数据），允许"不确定" | 清单已回填 |
| S1.3 ★ 定形态 | 拿清单定"它活在哪"，给 4 个形态选项 + 推荐 + 代价 | 已选定一项 |
| S1.4 补全需求 | 四要素（场景/目标/约束/验收）＋ 数据旅程扫"断多假错慢挂丢漏" | 每个缺口都有"怎么办" |
| S1.5 信息架构 | 仅 UI 类产品：关键任务 → 页面 → 每个能点的地方点完去哪 | 无死胡同；否则跳步留痕 |
| S1.6 边界与禁区 | 明确不做什么 + 合规红线 + 内部概念不外露 | 明确不做 ≥ 1 条 |
| S1.7 验收 + MVP | 逼成可验证标准，优先 EARS 格式；定 MVP 完成线 | ≥ 1 条可验证验收 + MVP 线 |
| S1.8 技术栈雏形 | 拿资源清单反推，别默认后端+数据库+Python | 选定 + 否决都写明 |
| S1.9 落盘 | `interview_finalize` 写文档，提议 HTML 原型 | 两份文件已写 |

**轻模式可以"几步合并、一次报门"**（S1.0+S1.1+S1.2 / S1.3+S1.4+S1.6 / S1.7+S1.9），但**出口门无论轻重都不打折**——省的是停顿次数，不是产出质量。

## 岔路口建议库

### 形态：它活在哪

| 形态 | 适合 | 代价 / 提醒 |
|------|------|-----------|
| 纯前端网页（无后端、无服务器） | 展示型官网、留资、工具型小页面 | 最省心，能扔到任何静态托管；"提交后存哪"留作后续 |
| 需要一台常开服务器 | 要存数据、要登录、多人协作、定时任务 | 复杂度和维护成本跳一档——你得管这台机器 |
| 可直接运行的单文件 / 脚本 | 自己或少数人用的小工具 | 最简单；但没界面、要会运行，不适合给小白用户 |
| 零代码 / 自动化平台 | 完全不想碰代码、逻辑不复杂 | 上手快；但有订阅费、逻辑一复杂就难维护 |

> **默认推"够用的最简形态"。** 展示型官网 + 留资类产品，纯前端网页 + 表单就够了。不要因为"显得正经"就给人加上他养不起的后端。

### 技术栈：抵制 AI 爱加料

| AI 爱推荐 | 它解决的问题 | 替用户反问 |
|-----------|------------|-----------|
| Docker | 环境一致性 | 我就一台机器、一个人，需要吗？ |
| Nginx | 反向代理 / 负载均衡 | 我这访问量，需要吗？ |
| MySQL/PostgreSQL | 存大量数据 | 一个文件型数据库够用吗？ |
| Redis | 缓存加速 | 有人嫌慢吗？ |
| 微服务 / K8s | 大规模、多团队 | 我有几百台机器、几十号人吗？ |

## 落盘产出

- `docs/prd.md` —— 由插件按固定结构渲染：元信息、产品结论、用户场景与形态、信息架构、
  边界情况、验收标准、MVP 定义、以后再说。颗粒度量力而行。
- `docs/项目说明书.md` —— 后续每次对话都贴给 AI 的"活记忆"。
- `docs/进度账本.md` —— 流程唯一状态来源，插件自动维护，不必手改。
- 下一步（提议，不强求）：HTML 交互原型——最便宜的需求验证器。

## 出口门（声称 S1 完成前必过）

`interview_finalize` 会逐条自检并返回 pass/fail。**只要有一条 error 未通过，它就不会写任何文件**：

- 必经步骤全部 ✅、跳过的可选步骤有留痕
- PRD 元信息（文档状态 / 版本 / 产品名称）已填，版本形如 v0.1
- 核心定位是一句完整的话（≥ 10 字）
- 明确不做 ≥ 1 条
- 「它活在哪」已选定
- 验收标准 ≥ 1 条且具体可验证（"系统正常"这类空话会被拒绝）
- MVP 完成定义 ≥ 1 条
- 需求基准描述覆盖场景 / 目标 / 约束 / 验收
- 无占位符残留、无英文正文、无密钥等敏感信息

> v0.2 起这两条自检不再误伤正当写法：URL、路由、行内代码里的 `<id>` / `<标签>` 不算占位符；
> 标题里的三段式品牌名（"Land of Knowledge"）不算英文正文。真被判成英文正文的，把品牌名 / 术语
> 放进 `interview_finalize` 的 `terms` 重新过门，**不要为了让自检通过去改产品名或改写法**。

全过之后才落盘，并声明：

> ✅ S1 出口门通过：prd.md / 项目说明书.md 已写、账本 S1 已标完成、无占位符、格式合规。

## 别做的事

- 不要在用户没答完时调用 `interview_finalize` 硬闯——它只会返回一堆 blocking，白跑一趟。
- 不要把必经步骤当可选步骤跳过：`interview_skip` 会拒绝，并告诉你必须问出什么。
- 不要把密钥、密码、token 写进 `interview_advance`——账本和文档都会落盘。
- 不要为了"少几次调用"把一步的字段一次性塞给 `interview_advance`：分步提交才是省事的做法，
  一次塞太多正是整轮被中止的成因。
- 不要往 `interview_*` 里传 profile 目录、临时目录或别人项目的目录：账本会落在那里，之后就会被当成那个项目的进度。
- 不要为了过自检去改产品名、把 `/posts/<id>/` 改写成中文描述——那是自检的误伤，用 `terms` 白名单解决。
